# authchecker (модуль 4)

`authchecker` — четвёртый модуль дипломной утилиты. Для короткого запуска он
принимает точную страницу входа или TXT-файл найденных страниц; отчёт
PointFinder `report.json` схемы `2.0` остаётся вариантом для подробного
плана и повторяемой проверки. Задания выполняются через единый scheduler
с ограничениями и аудитом.

Есть два режима: безопасный `plan`/`run --dry-run` без сети и ограниченный
`run --live`. Live-режим поддерживает `http_basic` и простые POST
`password_form` и ограничивает цели указанным либо однозначно определённым из
отчёта доменом. Поддомены разрешаются только с явным флагом. Запросы выполняются
напрямую либо через необязательный HTTP proxy.

Основная связка отдельных модулей через общую команду:

```bash
goad discover -u https://example.com -t bitrix --slow --links-output auth-links.txt --no-json
goad check -u auth-links.txt -l admin -p 'пароль' --max-per-account 1 --rate 1
```

Для списка паролей укажите `-p passwords.txt` или явный
`--passwords passwords.txt`. `-p` распознаёт один существующий файл и читает
его потоково; для буквального пароля, совпадающего с именем файла, используйте
`--password`.

Можно передать одну известную страницу напрямую: `goad check -u
https://example.com/bitrix/admin/ -l admin -p 'пароль' --max-per-account 1 --rate 1`.
Шаблон определяется автоматически; `-t bitrix` необязателен и сужает
проверку только до этого продукта.
Модуль 4 повторно анализирует только переданные страницы. Если шаблон не
совпал, попытки входа не начинаются. Для нескольких хостов требуется
`--scope-domain DOMAIN --allow-subdomains`.

Короткий запуск по уже сохранённому отчёту тоже доступен:

```bash
goad check -r report.json -l student -p 'пароль' --max-per-account 1 --rate 1
```

Для live-проверки нужно явно указать `--max-per-account N` и скорость:
`--rate N` или `--slow` (одна попытка в 15 секунд). `--max-total` необязателен.
Короткий запуск автоматически задаёт точный хост единственной цели и создаёт
уникальный audit JSONL рядом с файлом ссылок/отчётом или в текущем каталоге
для одной ссылки. Если в отчёте несколько хостов,
нужно указать `--scope-domain` и при необходимости `--allow-subdomains`.
Для предварительного плана без сетевых запросов добавьте `--dry-run`.
Подробная форма `goad check run ...` остаётся доступной.

## Общие продуктовые шаблоны

PointFinder распознаёт продукт и передаёт в `report.json` не только поля,
но и необязательный `metadata.login_verification` (`form-check/1`). Для
административного входа 1С-Битрикс основной полный шаблон находится в
[`bitrix.yaml`](../discovery_module_3/src/authpoints/data/login_templates/bitrix.yaml).
Правила редактируются там; при запуске `check -u ... -t bitrix` они
считываются заново, поэтому JSON вручную создавать не нужно. При запуске
`check -r report.json` после изменения шаблона нужно заново создать отчёт.
Готовый отчёт самодостаточен: установка PointFinder/YAML для его проверки
в отдельном `authchecker` не требуется.

```bash
pointfinder -u urls.txt -t bitrix --slow --output bitrix-report.json
authchecker plan --report bitrix-report.json --logins logins.txt --passwords passwords.txt
authchecker run --live --report bitrix-report.json --logins logins.txt --passwords passwords.txt --scope-domain example.com --audit bitrix-audit.jsonl --max-total 2 --max-per-account 2 --slow --compact
```

Шаблон Bitrix определяет поля `USER_LOGIN`/`USER_PASSWORD`, служебные
`AUTH_FORM=Y` и `TYPE=AUTH`, свежую сессию и обязательный для него `sessid`.
При `action: fixed` POST идёт на `/bitrix/admin/?login=yes` из шаблона.
Структура `<form>`, типы и видимость полей не нужны: параметры берутся из raw.
Перед POST заново проверяются признаки `detection`, сохранённые в отчёте.
Перед каждой парой выполняется GET в новой cookie-сессии. При `transport: auto`
если предварительный HTTP-разбор не может получить нужную страницу/токен, подключается
headless Chromium для DOM и cookies; затем отправляется HTTP-запрос шаблона
без заполнения полей или нажатия кнопки. После отправленного POST повтор через другой транспорт
не выполняется. Для fallback нужны Playwright и Chromium (установка ниже).

Теперь запрос редактируется непосредственно в `verification.request.raw`:

```http
POST /bitrix/admin/?login=yes HTTP/1.1
Host: {{host}}
Content-Type: application/x-www-form-urlencoded
Origin: {{origin}}
Referer: {{page_url}}

AUTH_FORM=Y&TYPE=AUTH&USER_LOGIN={{login}}&USER_PASSWORD={{password}}&Login=&captcha_sid=&captcha_word=&{{form_fields}}
```

Путь POST указан явно; `{{host}}` — хост страницы с портом,
`{{origin}}` — её протокол и хост.
`{{login}}`/`{{password}}` автоматически URL-кодируются. `{{form_fields}}` добавляет
только динамические поля, объявленные в `csrf_fields`, без повторения констант.
Cookies и Content-Length формируются во время проверки, а не копируются в YAML.
При `--browser-http` запрос уже известен: браузер только подготавливает страницу
и свежую сессию, захват формы не требуется. Результат проверяется по HTTP-ответу;
JSON/шифрование и JS-only подтверждение входа не объявляются поддержанными.
Полное описание формата — в [инструкции по шаблонам](../discovery_module_3/src/authpoints/data/login_templates/README.md).
Старые отчёты со структурированным `request` без `raw` остаются совместимыми.
Прежний сценарий HTML-форм сайта сохранён в `bitrix-site.yaml` (`-t bitrix-site`)
с действовавшими ранее правилами поиска полей и action формы.

Результат определяется правилами конкретного YAML. Для админки Bitrix
текущий положительный признак — ответ
`(window.BX || window.parent.BX).AUTHAGENT.setAuthResult(false);`, отказ —
`Неверный логин или пароль`, CAPTCHA — `"CAPTCHA":true`, второй фактор —
поле `USER_OTP`. У `bitrix-site` используются другие правила: видимая ссылка
выхода `logout=yes` или форма выхода с кнопкой. Один код 200/303, cookie или
оставшаяся форма сами по себе не подтверждают вход. Если признаки не совпали
либо противоречат друг другу, результат остаётся неопределённым.

Прямой `--browser --url` без отчёта по-прежнему использует общие эвристики:
он не читает каталог продуктовых шаблонов. Для использования новых правил
nужен свежий отчёт. GitLab и WordPress также передают продуктовые правила
проверки; OWA, Roundcube и Zimbra пока передают только признаки продукта.
Старые отчёты без `login_verification` сохраняют прежнее поведение.
Облачный Bitrix24/SSO и произвольно изменённые
JSON/шифрованные формы этим шаблоном не покрываются.

## Установка и тесты

Требуется Python 3.11 или новее.

```powershell
cd check_module_4
py -3.11 -m pip install -e .
py -3.11 -m unittest discover -s tests -v
```

Обычный HTTP-режим не имеет сторонних runtime-зависимостей.

### Проверка через браузер

Для страниц с JavaScript и форм, которые обычный HTTP-разбор не может
воспроизвести, есть отдельный режим:
форма загружается и отправляется внутри одной сессии Chromium. Установка из
корня проекта:

```bash
.venv-linux/bin/python -m pip install -e './check_module_4[browser]'
.venv-linux/bin/python -m playwright install chromium
```

```bash
goad run --browser \
  --target http://127.0.0.1:8080/login \
  --login student --password password123 \
  --browser-timeout 60
```

Окно видно по умолчанию; `--headless` скрывает его. Прямой вызов модуля 4:

```bash
goad check run --live --browser \
  --url http://127.0.0.1:8080/login \
  --login student --password password123 \
  --max-per-account 1 --rate 1 \
  --audit ./browser-audit.jsonl --compact
```

Можно повторять `--login`/`--password` или передавать файлы
`--logins`/`--passwords`, по одному значению в строке. Короткий `run` также
принимает списки через `-l`/`-p`, как в обычном режиме. Для каждой пары
создаётся новая браузерная сессия: страница загружается и форма отправляется
внутри неё. PointFinder и обход не запускаются. Режим не совместим с
`--report`, `-u`, `-q`, `--discover-only` или поиском логинов.

```bash
goad run --browser \
  --target http://127.0.0.1:8080/login \
  --login student --passwords ./passwords.txt \
  --max-total 3 --max-per-account 3 --rate 1 --threads 2
```

Для `goad run` действуют его собственные значения по умолчанию; для
отдельного `goad check --live` лимит `--max-per-account` и скорость
`--rate`/`--slow` указываются явно. Верхние границы: `--max-total` — 1000,
`--rate` — 10, `--threads` — 10. В отдельном `goad check` значение
`--max-per-account` должно быть положительным; у `goad run` остаётся
собственный максимум 20.
В браузерном режиме лимиты считают проверки
пар, включая случаи без отправки пароля. Каждая проверка отправляет не более
одной авторизации, поэтому число отправок не превышает `--max-total`.
`--rate` ограничивает частоту старта браузерных проверок и отдельно отправку
авторизационных POST между потоками. Загрузка ресурсов страницы создаёт
дополнительные запросы и этим флагом не регулируется.
`--threads` задаёт число одновременно работающих браузерных сессий.

После успеха, OTP/MFA или блокировки новые попытки для данной учётной записи
прекращаются. Результат `unsupported`, включая challenge, прекращает задание
для URL; HTTP 429 останавливает весь запуск. Уже начатые параллельные
проверки могут завершиться.

При OTP/MFA краткий вывод показывает логин и пароль пары, после которой
появился запрос кода, с пометкой «вход не завершён». Это признак прохождения
первого шага, а не подтверждённый вход в аккаунт. Пароль не сохраняется в
JSON-отчёте и audit, но попадает в вывод консоли и его полный журнал.

`checked_count` в отчёте считает запущенные проверки, а `attempted_count` —
фактические отправки авторизации. `--max-total` является верхней границей:
например, `halt_reason: "unsupported:scope"` означает, что запрос вышел за
разрешённую область и следующие пароли для этой точки не проверялись.
Для диагностики выводятся только origin, метод и тип заблокированного запроса
(`blocked_origin`, `blocked_method`, `blocked_request_type`), без пути,
параметров или тела запроса.

`--success-selector '.account-menu'` и `--failure-selector '.login-error'`
задают видимые CSS-признаки результата. Без надёжного признака результат
будет `ambiguous`, а не успехом только по HTTP 200/303. При OTP/MFA или форме
только с email утилита сообщает причину остановки. Если появилась защитная
страница, в видимом окне утилита ждёт появления формы до `--browser-timeout`;
в `--headless` сразу сообщает о challenge. Автоматических действий для решения
CAPTCHA нет.

`--proxy`, `--ca-cert` и `--user-agent` применяются к браузерному режиму.
Браузер использует собственную сеть и временную сессию; внешние ресурсы
страницы могут загружаться, но пароль отправляется только исходному origin.
С `--ca-cert` сначала проверяется цепочка и имя целевого HTTPS-сервера через
указанный прокси. Затем для этой сессии Chromium разрешаются сертификаты с
ключами проверенного сервера и переданного CA (SPKI); системное доверие не
меняется. Это временное исключение по ключу, а не установка CA: если прокси
выдаёт сторонним ресурсам сертификаты с другими ключами без полного chain,
некоторые ресурсы могут остаться недоступны. Нужен локальный `openssl`.
Для внешнего URL при прямом `check run` нужен `--scope-domain`; короткий
`goad run --target` берёт область из адреса автоматически.
`--browser-timeout` принимает 1–300 секунд. Найденные имена полей и этапы
появляются в stderr; результат — в stdout. Пароли, cookies и тело ответа в
аудит не записываются; HTML и скриншоты автоматически не сохраняются. Полные
URL, включая токены в query-параметрах, записываются без маскировки: защищайте
каталог артефактов.
`--save-report` в этом режиме сохраняет результат формата
`browser-check/1`, который не является отчётом PointFinder и не подходит для
`check --report`. Короткий `run` создаёт его в своём каталоге `artifacts`.

### Один браузерный запуск и HTTP-проверки

В обоих браузерных режимах известные cookie-диалоги закрываются только
кнопкой отказа от необязательных cookies. «Accept all» автоматически не
нажимается. Если диалог не распознан, видимый браузер ждёт ручного выбора;
в `--headless` проверка останавливается с причиной `cookie_consent`.

`--browser-http` один раз открывает точную страницу в браузере и получает
шаблон запроса вместе с cookies. Авторизация на этом этапе перехватывается до
выхода в сеть; затем Chromium закрывается. Дальнейшие пары проверяются
HTTP-клиентом с теми же `--max-total`, `--max-per-account`, `--rate` и
`--threads`. Для каждой проверки создаётся своя CookieJar, а GET страницы
входа обновляет скрытые поля и CSRF-токен.

Важное отличие: копия CookieJar может ссылаться на ту же серверную сессию.
Поэтому HTTP-проверки одной захваченной сессии выполняются последовательно,
даже при `--threads 2`. Иначе успешный вход одной пары мог бы дать ложный
успех другой. Перед каждой попыткой проверяется, что страница ещё не
авторизована; если уже авторизована, новый пароль не отправляется.
Для независимых параллельных браузерных сессий используйте `--browser`.

```bash
goad run --browser-http \
  --target http://127.0.0.1:8080/login \
  --login student --passwords ./passwords.txt \
  --max-total 3 --max-per-account 3 --rate 1 --threads 1
```

Прямой вызов: `goad check run --live --browser-http --url URL` с
обычными источниками логинов/паролей, явными `--max-per-account` и
`--rate`/`--slow`, областью `--scope-domain` для внешних целей и обязательным
`--audit FILE`. Режим несовместим с `--browser` и
`--report`; в коротком `run` он требует `--target` либо `--targets-file`
и не запускает обход.
`--headless`, `--browser-timeout`, `--success-selector`, `--failure-selector`,
`--proxy`, `--ca-cert` и `--user-agent` поддерживаются в обоих режимах.
`--timeout` задаёт ожидание HTTP-запроса после браузерного этапа.

Поддерживаются URLencoded- и JSON-запросы. JavaScript, вычисляющий динамические
значения для каждой пары, может потребовать полноценный `--browser`;
неподдерживаемый шаблон возвращается как `unsupported`.
В HTTP-режиме селекторы результата поддерживают простые `#id`, `.class`,
`tag` и `[attr=value]`; сложные браузерные CSS-селекторы не поддерживаются.
При JSON-ответе на POST проверяется не только HTTP-код: сообщение вида
`{"result":"error","message":"Имя пользователя или пароль указаны неверно."}`
означает подтверждённый отказ. Общий `result: error` или `success: false`
без признака неверной пары не считается неверным паролем; результат остаётся
неопределённым. Для успеха нужен явный признак авторизации, например
`authenticated: true` или элемент выхода из аккаунта; один лишь HTTP 200
либо `result: success` недостаточен. Текст ответа и токены не записываются в аудит.
Обычная HTTP-проверка формы использует те же JSON-признаки. Если после POST
или редиректа на той же странице остаётся видимая парольная форма, результат
считается неуспешным, кроме случаев ошибки CSRF или шага MFA. Без явных
признаков выводится «результат не определён».
Простое копирование запроса и cookies не гарантирует перенос сессии или проверки Cloudflare в
другой HTTP-клиент. При защитной странице в HTTP-ответе задание останавливается
с диагностикой, без повторного запуска браузера на каждый пароль.

В аудит и `browser-check/1` записывается `mode: "browser_http"`,
`transport: "http"`; сырой перехваченный запрос, его тело и cookies не
сохраняются. Токены в URL сохраняются без маскировки. Успешная пара выводится только в результат CLI, как в других
live-режимах.

### Файл готовых страниц входа

Короткий `goad run` принимает файл целей вместо одиночного `--target`:

```bash
goad run --browser-http \
  --targets-file ./targets.txt \
  --login student --passwords ./passwords.txt \
  --max-total 3 --max-per-account 3 --rate 1 --threads 1
```

В `targets.txt` нужен один полный HTTP(S) URL страницы входа на строку.
Поддерживается UTF-8 с BOM или без него, а также CRLF. Пустые строки и строки,
начинающиеся с `#`, игнорируются; дубликаты исключаются с сохранением порядка.
`--urls-file` является алиасом `--targets-file`.

Файл доступен в обычном HTTP-режиме, `--browser` и `--browser-http` именно через
`goad run`. Прямой `goad check run` по-прежнему получает один
`--url`. Обход и стандартные пути не запускаются. Файл несовместим с
`-u`/`--url`, `--target`, `-q`, `--discover-only`, `--find-logins` и
`--search-engine`.

Цели обрабатываются последовательно, с отдельной областью и сессией для каждой.
Ограничения `--max-total`, `--max-per-account`, `--rate` и `--threads` действуют
на каждый URL отдельно. Например, два URL с `--max-total 3` допускают до шести
проверок, а не трёх на весь файл. Потоки относятся к проверкам внутри одного
URL; HTTP-пары одной захваченной браузерной сессии остаются последовательными.

Отдельные результаты находятся в `artifacts/<запуск>/001/report.json`,
`001/audit.jsonl`, затем `002/...` и т. д. Явный `--audit FILE` дописывает
события всех целей в общий файл вместо отдельных audit. Явный `--save-report`
сохраняет сводный JSON пакета, не перезаписывая отчёты отдельных URL.
`--json` выводит один сводный JSON; обычный вывод содержит короткую строку на
URL, а сведения о пакетном запуске идут в stderr без учётных данных.

## CLI

Проверить отчёт:

```powershell
authchecker validate .\report.json
```

Построить план без сетевых запросов. Логин и пароль можно передать прямо в CLI:

```bash
authchecker plan \
  --report ./report.json \
  --login student \
  --password password123
```

Для нескольких значений повторяйте `--login` и `--password`. Вместо них можно
передать `--logins ./logins.txt` и `--passwords ./passwords.txt`. Пары
`--login`/`--logins` и `--password`/`--passwords` взаимоисключающие.

Dry-run с записью краткого JSONL-события аудита:

```bash
authchecker run --dry-run \
  --report ./report.json \
  --login student \
  --password password123 \
  --audit ./attempts.jsonl
```

## Live через Burp

Укажите свободный порт Burp listener, например `127.0.0.1:9090`.
Отключите Intercept либо вручную нажимайте Forward для каждого запроса.

```bash
goad check run --live \
  --report ./report.json \
  --login student \
  --password password123 \
  --proxy http://127.0.0.1:9090 \
  --rate 2 \
  --threads 4 \
  --max-total 100 \
  --max-per-account 3 \
  --audit ./attempts.jsonl
```

### Точечная проверка одной ссылки

Готовый `report.json` необязателен, если известен точный URL страницы входа или
HTTP Basic endpoint. `--url` передаёт эту ссылку PointFinder: он выполняет один
GET через тот же proxy, распознаёт точку входа и возвращает результат модулю 4.

```bash
goad check run --live \
  --url http://127.0.0.1:8080/login \
  --login student \
  --password password123 \
  --proxy http://127.0.0.1:9090 \
  --rate 2 \
  --threads 4 \
  --max-per-account 1 \
  --save-report ./exact-login-report.json \
  --audit ./attempts.jsonl
```

`--report` и `--url` взаимоисключающие. Точечный режим не обходит сайт и не
перебирает стандартные пути: переданная ссылка должна вести непосредственно на
HTML-форму либо отвечать HTTP Basic challenge. Если PointFinder не находит
поддерживаемую точку, попыток входа не выполняется.
Обычные POST-формы со скрытыми полями HTTP-режим загружает заново перед каждой
попыткой: берёт свежие значения и cookie из той же сессии. Если поля создаются
JavaScript или форма отправляется через JS, используйте `--auto-browser` или
`--browser-http`. Автоматического SSO-сценария нет.
Если найден только первый шаг с логином/email без пароля, модуль 4 остановится
с пояснением. Шаги отправки OTP/письма не выполняются автоматически. Браузерный
поиск может открыть переключатель «Sign in» или «Use password», если он не
отправляет форму, и повторно проверить DOM на поле пароля.
`--save-report` необязателен; без него отчёт передаётся между модулями в памяти.

Для внешнего разрешённого домена задайте scope явно:

```bash
goad check run --live \
  --url https://auth.site.example/login \
  --scope-domain site.example \
  --allow-subdomains \
  --login student \
  --passwords ./passwords.txt \
  --proxy http://127.0.0.1:9090 \
  --ca-cert ./burp-ca.pem \
  --max-per-account 3 --rate 1 \
  --audit ./attempts.jsonl
```

Основной домен и его поддомены разрешены, остальные хосты отклоняются до
сетевого запроса. Без `--scope-domain` сохранён совместимый локальный режим:
только `http://127.0.0.0/8` и `http://localhost`.

`--slow` включает щадящий live-профиль: не чаще одной попытки в 15 секунд и
один поток. Он не уменьшает `--max-total` и `--max-per-account`.

`--rate` задаёт общую для всех потоков частоту старта попыток: значение должно
быть больше 0 и не больше 10 запросов в секунду. `--threads` задаёт максимум
одновременно выполняемых попыток и принимает значения от 1 до 10; без флага
работает один поток. Например, `--rate 2 --threads 4` допускает до четырёх
одновременных запросов, но запускает новые попытки не чаще одной в 0,5 секунды.
Точечный GET-анализ `--url` выполняется отдельно до попыток авторизации.

В интерактивном терминале `check --live` обновляет одну строку прогресса:
отправленные попытки, верхнюю оценку оставшихся и число обработанных проверок.
При перенаправлении вывода строка не печатается; итог и события остаются в
журнале и обычном результате. Успех, блокировка или неподдерживаемая форма
могут завершить работу раньше рассчитанного максимума.

По умолчанию `goad check run --live` печатает подробный JSON. Добавьте
`--compact`, чтобы получить одну короткую строку на endpoint:

```text
[УСПЕШНО] http://127.0.0.1:8080/login — логин: student — пароль: password123
[НЕУСПЕШНО] http://127.0.0.1:8080/admin — попыток: 3
```

Для обычной HTTP-формы сам по себе ответ 200 или редирект 302/303 не
подтверждает вход. После редиректа утилита проверяет конечную страницу через
GET в пределах того же origin, сохраняя cookies только на время одной попытки.
Признаком входа служит доступный элемент выхода из аккаунта в HTML при
отсутствии поля пароля. Видимость определяется по разметке и inline-стилям;
внешние CSS в этом HTTP-режиме не вычисляются. Если подтверждающих признаков
нет, результат остаётся неопределённым. Признаки отказа ищутся в тексте
страницы: слова в JavaScript, явно скрытых элементах и HTML-атрибутах вроде
`aria-invalid="false"` не означают неверный пароль.

Краткий вывод различает подтверждённый отказ, неопределённый результат,
сетевую ошибку и неполную проверку. Сообщение `[НЕУСПЕШНО]` означает, что все
выполненные проверки этого URL дали подтверждённый отказ. Причины остальных
исходов выводятся отдельно; подробные статусы сохраняются в JSON и аудите:

```text
[РЕЗУЛЬТАТ НЕ ОПРЕДЕЛЁН] ... — ответ не подтверждает ни вход, ни отказ
[ОШИБКА СЕТИ] ... — не удалось получить ответ
[ПРОВЕРЕНО ЧАСТИЧНО] ... — часть проверок не поддерживается или пропущена
```

Короткая команда `goad run` включает этот формат автоматически; для
возврата подробного JSON используйте `goad run ... --json`.

Live не читает `HTTP_PROXY`/`NO_PROXY`: proxy используется только при явном
`--proxy http://host:port`. Поддерживаются Burp Suite, OWASP ZAP, mitmproxy,
корпоративные и удалённые HTTP-прокси. Для HTTP передаётся абсолютный target
URL, для HTTPS создаётся CONNECT-туннель с проверкой сертификата. `--ca-cert`
позволяет доверять экспортированному CA перехватывающего proxy. В обычном
HTTP-режиме скрытые поля POST-формы обновляются отдельным GET перед каждой
попыткой. Если форма или токен не найдены, пароль не отправляется. Формы не с
методом POST остаются неподдерживаемыми в обычном HTTP-режиме.

Все переданные входные пути (`--report`, `--logins`, `--passwords`) проверяются до
планирования или сетевого запроса. Отсутствующий аргумент, несуществующий файл
или каталог вместо файла завершают команду с кодом 2. При запуске
`goad` из другого каталога используйте абсолютные пути: относительные
пути всегда считаются от текущего рабочего каталога.

Успешный пароль выводится вместе с логином в результате live-запуска, но не
попадает в `report.json` или audit. Значения `--password` также остаются в
истории оболочки и могут быть видны в списке процессов. Для чувствительных
значений используйте `--passwords FILE`.

В dry-run по умолчанию в задания проходят `password_form`, `http_basic`,
`http_digest`, `ftp`, `ftps` и `ssh`. Точный allowlist для анализа можно задать
повторяемым аргументом `--auth-type`. SSO, passwordless и JS-login остаются в
отчёте как неподдерживаемые и не превращаются в попытки.

В live по умолчанию выбираются только `password_form` и `http_basic`.

## Контракт данных

- Импортёр повторяет `report.schema.json` PointFinder 2.0: обязательные поля,
  запрет дополнительных полей, типы, диапазоны портов, уникальность списков,
  шаблон `finding.id`, UUID и date-time проверяются до планирования.
- `partial: true` допустим: корректные `findings` такого отчёта обрабатываются.
- `services` строго валидируется, но никогда не используется как источник
  заданий.
- `job_key` включает `run_id`, `finding.id`, endpoint, auth type,
  `metadata.auth_fingerprint` и `metadata.form_action`. Поэтому формы с
  совпавшим `finding.id`, но разным обработчиком или fingerprint, не сливаются.
- Загрузчик паролей поддерживает выбранную кодировку и удаляет только `CR/LF`.
  Пробелы, табы и пустые пароли сохраняются. Логины читаются строго как UTF-8.

## Политика и аудит

`AttemptPolicy` задаёт один режим работы: общую скорость, общий максимум и
максимум на пару «задание + логин». Результаты `success`, `mfa_required` и
`locked_out` закрывают эту пару и не мешают проверить другие аккаунты;
`rate_limited` немедленно останавливает весь запуск. Эти безопасные значения
можно менять через явные параметры политики, без создания отдельных режимов
`lab/audit`.

`JsonlAuditWriter` не пишет пароли ни при каком результате. Для корреляции в
рамках процесса используется ключевой HMAC `secret_ref`; секрет также
вырезается из detail/evidence, а чувствительные ключи редактируются.

## Расширение адаптерами

Адаптер реализует `AuthAdapter.auth_types` и один ограниченный вызов
`attempt(job, credential) -> Outcome`, после чего регистрируется:

```python
registry = AdapterRegistry()
registry.register(MyHttpBasicAdapter())
scheduler = Scheduler(registry, AttemptPolicy())
result = scheduler.run(attempt_stream)
```

Если адаптера нет, registry возвращает безопасный `UnsupportedAdapter`, который
не обращается к сети и выдаёт `OutcomeStatus.UNSUPPORTED`.
