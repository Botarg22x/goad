# Шаблоны логинок PointFinder

Один сценарий входа — один UTF-8-файл `.yaml` или `.yml` в этом каталоге.
Все такие файлы загружаются автоматически (без обхода вложенных каталогов).
Это собственный формат PointFinder, не формат Nuclei.

Все встроенные шаблоны теперь имеют одинаковый порядок разделов:
`id`, `label`, `category`, `paths`, `detection`, необязательный `verification`.
`detection` описывает, **как найти** страницу; `verification` — **как проверить**
пару логин/пароль. Для OWA, Roundcube и Zimbra известны только признаки формы,
поэтому `verification` в их файлах пока нет: запрос входа не выдумывается.

Для своего продукта скопируйте `PRODUCT_TEMPLATE.yaml.example` в новый файл
`название-продукта.yaml` и замените строки в кавычках. Пока расширение
`.example` на месте, образец не загружается. Готовые примеры: `bitrix.yaml`
для страницы админки без обычной формы, `gitlab.yaml` для JS-полей,
`wordpress.yaml` для HTML-формы. Старые короткие и плоские YAML-файлы
по-прежнему читаются, но новые лучше писать в едином виде.

## Единый вид

```yaml
id: myportal
label: Мой портал
category: webapp
paths: [/login/]

detection:
  username_fields: [username]
  password_fields: [password]
  signals_any:
    - in_body: 'data-product="myportal"'

verification:
  schema: form-check/1
  transport: auto
  request:
    session: fresh
    csrf_fields: []
    raw: |-
      POST {{action}} HTTP/1.1
      Host: {{host}}
      Content-Type: application/x-www-form-urlencoded

      username={{login}}&password={{password}}&{{form_fields}}
  result:
    success_any:
      - in_body: 'data-authenticated="true"'
    failure_any:
      - in_body: 'Неверный логин или пароль'
    captcha_any: []
    mfa_any: []
    csrf_error_any: []
```

Для формы в `detection` задаются имена полей и дополнительные признаки;
оба поля должны быть в одной доступной форме. Для страницы без обычной формы
вместо них используются `status_codes` и `match` (см. `bitrix.yaml` и
`gitlab.yaml`); поля логина и пароля тогда берутся из `request.raw`.
`paths` нужны только для поиска страниц, а не для отправки пароля.
`verification` можно не писать, если пока известны только признаки продукта.

## Совместимость: прежний короткий шаблон

```yaml
id: myproduct
paths: [/login/]
in_body: 'data-product="myproduct"'
post: 'username={{login}}&password={{password}}'
success: 'data-authenticated="true"'
success_status: 302
failure: 'Неверный логин или пароль'
failure_status: 200
```

- `paths` — адреса, на которых искать страницу. При `--page-only` стандартные
  пути не обходятся, проверяется только переданный URL.
- `in_body` — отличительная строка из ответа страницы входа. Можно указать
  список: тогда должны совпасть **все** строки. Совпадение буквальное,
  с учётом регистра. Выбирайте строки, не встречающиеся на других страницах.
- `post` — тело известного запроса входа. Замените значение логина на
  `{{login}}`, пароля — на `{{password}}`; имена полей слева оставьте реальными.
  Заголовки, cookies и кодирование значений утилита добавит сама.
- `success` и `failure` — необязательные характерные строки ответа после
  отправки запроса. Вместо `success` можно указать `success_link_query` или
  `success_form_fields`; при нескольких вариантах строки задаются списком.
- `success_status` и `failure_status` — коды **ответа на POST** (например, 302
  и 200). Допускается указать только один код либо оба кода без строк
  `success`/`failure`. При наличии и кода, и строки должны совпасть оба условия.
  Если указан только `failure_status`, остальные ответы остаются неопределёнными.
  Для `success_status` дополнительно требуется итоговая страница HTTP 2xx без
  видимой формы пароля. Код 302 сам по себе — ненадёжный признак: если сайт
  редиректит на страницу без формы и при неверном пароле, возможен ложный
  успех. Для надёжной проверки добавьте `success` или другой признак входа.

По умолчанию POST отправляется на `action` найденной HTML-формы, а поля логина
и пароля должны быть в этой форме. Если продукт отправляет POST на текущую
страницу без обычной формы, добавьте `post_to: page`. Если из захваченного
запроса известен другой путь на том же сайте, укажите `post_to: /путь?query=1`.
В этих режимах можно добавить `path_contains: /login/` и
`csrf_fields: [имя_токена]`; `alternate_in_body` задаёт второй набор строк
для распознавания страницы, `not_in_body` исключает нежелательные страницы.
Для CAPTCHA, OTP и ошибки сессии есть необязательные `captcha`, `mfa`,
`csrf_error` (строки ответа), а также `captcha_field` и `mfa_field` (имена
видимых полей). При совпадении соответствующего признака проверка
останавливается или помечается как требующая второго фактора. Правила `success` не должны встречаться до входа:
в таком случае утилита не подтвердит успешную пару.

Проверьте YAML без сетевых запросов: `pointfinder --list-templates`. Затем
проверьте только свою страницу: `pointfinder -u https://example.com/login/ --page-only -t myproduct`.
Если нужный POST уходит на отдельный API-адрес или для результата надо
проверять не тело ответа, используйте расширенный формат ниже.

## Подробности единого формата

Ниже описаны дополнительные признаки и правила, применимые к единому формату.

В `detection` доступны код, путь, заголовок страницы, текст, имена полей и
пути ресурсов, а также `in_body` — буквальная строка из тела ответа.
Проверка HTTP-заголовков в условиях пока не предусмотрена.
В `request.raw` задаётся известный запрос входа, в `result` — признаки ответа.
Скорость поисковых дорков Яндекса/Google относится к модулю Logingen,
а не к продуктовым шаблонам.

## Основной режим: распознавание страницы + HTTP-запрос

Образец страницы без обычной формы — `bitrix.yaml`: вход в административную часть 1С-Битрикс.
`-t bitrix` выбирает именно этот сценарий. Прежний шаблон обычных HTML-форм
сайта сохранён как `bitrix-site.yaml` / `-t bitrix-site`.

Полный шаблон содержит `id`, `label`, `category`, `paths`, `detection`, `verification`.
Поля `username_fields`, `password_fields`, `signals_any` в нём не нужны:
параметры запроса определяются непосредственно в `verification.request.raw`.

В `detection` задаются коды ответа и дерево признаков `match`:

```yaml
detection:
  status_codes: [200]
  match:
    all:
      - path_contains: /bitrix/admin/
      - field_names_all: [AUTH_FORM, TYPE, USER_LOGIN, USER_PASSWORD]
```

Это сокращённый пример синтаксиса. Текущий `bitrix.yaml` использует только
перечисленные в нём буквальные условия `in_body` и известный POST-запрос;
неподходящие страницы не добавляются автоматически по названию или URL.

- `all` — нужны все вложенные признаки; `any` — хотя бы один; `not` — исключить признак.
- `path_contains` — подстрока пути проверяемой страницы (не query и не action формы).
- `title_contains`, `text_contains` — подстрока заголовка/текста страницы.
- `in_body` — буквальная подстрока исходного тела ответа, включая HTML-теги,
  атрибуты и JSON. Регистр учитывается; HTML-сущности и пробелы не преобразуются.
- `asset_path_contains` — подстрока пути извлечённого ресурса/ссылки.
- `field_names_all` — присутствие перечисленных имён на странице: без требования
  одной формы, типа, видимости, доступности или единственного экземпляра.

Остальные подстроки сравниваются без учёта регистра, имена — с учётом.
`in_body` проверяется в декодированном теле одного ответа, без регулярных выражений;
при браузерном обходе используется HTML DOM после выполнения JavaScript.
Вставляйте короткую характерную строку (до 4096 символов, без перевода строки)
и заключайте её в кавычки YAML. Не вставляйте туда CSRF-токены, cookies
или персональные данные: текст правила копируется в JSON-отчёт. Правила не исполняют
Python/JavaScript. URL либо название Bitrix сами по себе не являются логинкой.
При совпадении полного шаблона общий подбор HTML-полей не выполняется.

Для страницы без обычной формы `verification.request` использует
`action: page` или `action: fixed`. В первом случае `POST {{action}}`
отправляет данные на распознанный URL (путь + query). Во втором — на
конкретный путь того же origin из первой строки `raw`; так устроены текущие
Bitrix и GitLab. Имена параметров, метод и константы берутся из `raw`.
`{{form_fields}}` добавляет только объявленные `csrf_fields` текущей страницы;
посторонние поля других форм не копируются. Одинаковые повторения токена
объединяются; разные/пустые значения останавливают проверку.

Перед отправкой повторно проверяются признаки страницы в свежей сессии.
Если нужен JavaScript, headless-браузер получает DOM и cookies, после чего
запрос из YAML отправляется по HTTP, без поиска полей и нажатия кнопки.
То же поведение используется при явном `--browser-http`: захват запроса не нужен,
поскольку запрос уже задан. CAPTCHA/OTP/429 останавливают проверку; после
отправленного POST повторного входа через другой транспорт нет.
Результат такого запроса определяется по HTTP-ответам и правилам `result`;
отдельный JS-сценарий подтверждения результата этим не реализуется.

Для проверки только переданной страницы:
`pointfinder -u https://example.com/bitrix/admin/ --page-only -t bitrix --slow`.

## Распознавание HTML-формы

Для HTML-формы раздел `detection` содержит `username_fields`,
`password_fields` и `signals_any`. Так устроены `bitrix-site`, WordPress,
Roundcube, OWA и Zimbra. Его ограничения не относятся к распознаванию
страницы без формы (`bitrix`, GitLab).

1. Создайте `myportal.yaml` по примеру ниже. Используйте пробелы для отступов.
2. Задайте уникальный `id`: маленькие латинские буквы, цифры, `_` и `-`,
   начиная с буквы. Имя файла рекомендуется делать таким же, как `id`.
3. Впишите значения HTML-атрибута `name` нужных полей и отличительные признаки
   продукта. Не копируйте условия существующего шаблона без изменений:
   при совпадении двух продуктов детектор оставляет форму без продуктового тега.
4. Выполните `pointfinder --list-templates`: команда загрузит и проверит все
   определения без сетевых запросов. Ошибка содержит имя файла; для синтаксиса
   YAML также указывается строка и столбец.
5. Проверьте свою страницу: `pointfinder -u https://example.com/myportal/login --page-only --login-template myportal`.
   Этот запуск не обходит ссылки и не выполняет попытки авторизации; при
   необходимости включается отрисовка страницы в браузере.

```yaml
id: myportal
label: MyPortal
category: webapp
paths:
  - /myportal/login
detection:
  username_fields: [account_id]
  password_fields: [secret]
  signals_any:
    - text_contains: MyPortal
    - path_contains: /myportal/login
```

При editable-установке новый или изменённый файл будет прочитан при следующем
запуске. Пересобирать и переустанавливать пакет не нужно. При обычной установке
wheel редактируется установленный каталог данных, а не отдельная копия исходников.
Для временного отключения переименуйте файл, например в `myportal.yaml.disabled`.
Удалённые/переименованные определения не загружаются. Файлы с одинаковым `id`
считаются ошибкой, даже если их имена различаются.

## Поля шаблона

- `id` — идентификатор для `--login-template` и тега в отчёте.
- `label` — название продукта для человека.
- `category` — дополнительный тег, например `cms`, `webmail` или `webapp`.
- `detection.username_fields` — варианты имён поля логина. Подходящий элемент формы
  должен иметь тип `text`, `email` или `tel`.
- `detection.password_fields` — варианты имён поля пароля с типом `password`.
- `detection.signals_any` — дополнительные признаки; достаточно одного совпадения.
- `paths` — непустой список путей от корня сайта для стандартного поиска.
  При `--login-template myportal` встроенный список путей берётся из этого
  шаблона. `--paths-file` имеет приоритет; `--page-only` и
  `--no-standard-paths` не запускают стандартные пути.

Имена полей сравниваются с учётом регистра. Поля логина и пароля должны быть
доступны и находиться в одной форме; несколько подходящих полей считаются
неоднозначностью. Название продукта или URL без формы не дают находку.
Общие проверки регистрации и смены пароля продолжают действовать.

В `detection.signals_any` каждая запись содержит ровно один из ключей:

| Ключ | Проверка |
| --- | --- |
| `text_contains` | Подстрока в заголовке страницы или тексте формы, не во всём HTML |
| `in_body` | Буквальная подстрока исходного тела ответа, с учётом регистра |
| `path_contains` | Подстрока в пути страницы или адреса отправки формы; не в query-параметрах |
| `asset_path_contains` | Подстрока в пути извлечённых ссылок/ресурсов; не поиск по всему HTML |
| `field_names_all` | Все перечисленные поля присутствуют в той же форме; скрытые тоже учитываются |

Проверки подстрок не учитывают регистр, `field_names_all` учитывает.
Пример признака: `- field_names_all: [AUTH_FORM, TYPE]`.
Строки, которые YAML может принять за другой тип (`on`, `off`, `null`, числа),
заключайте в кавычки. Неизвестные поля, повторяющиеся YAML-ключи, пустые
значения и несколько YAML-документов в одном файле отклоняются.

## Что получает модуль 4

Модуль 3 записывает в JSON-отчёт `metadata.login_template`, `metadata.tags`
и `metadata.credential_fields`. В режиме страницы имена берутся из raw,
`credential_fields_source: template` и `detection_mode: page_template` явно это
показывают; наличие элементов `<input>` не выдумывается. Правила `detection`
также копируются в `login_verification` для повторной проверки модулем 4.
Для HTML-формы имена подтверждаются найденными полями.
Модуль 4 читает отчёт, а не YAML. Старые отчёты остаются совместимыми.

Для HTML-формы адрес отправки берётся из обнаруженной формы; при `action: page`
используется URL страницы, при `action: fixed` — путь из `raw`.
`paths` — не адрес принудительной
отправки пароля. После изменения шаблона создайте новый отчёт модуля 3:
уже сохранённый отчёт автоматически не изменится.

## Полный шаблон модуля 3 + 4: Bitrix

`bitrix.yaml` содержит блок `verification`.
Он целиком копируется в `metadata.login_verification` отчёта. Модулю 4
не нужен установленный PointFinder для чтения готового отчёта; версия
контракта `form-check/1` проверяется до запуска. Старые шаблоны и отчёты
без этого блока продолжают использовать общие обработчики.

Пример поиска: `pointfinder -u urls.txt -t bitrix --slow`.
`-t`/`--login-template` выбирает продукты; прежний выбор инструментов теперь
записывается как `--tools katana` (Nmap и Subfinder по умолчанию выключены).

### HTTP-запрос для HTML-формы (`action: form`)

В `request.raw` записывается HTTP-запрос. Поля слева от `=` — реальные имена
параметров; `{{login}}` и `{{password}}` справа — места для текущей пары:

```yaml
request:
  session: fresh
  csrf_fields: [sessid]
  raw: |
    POST {{action}} HTTP/1.1
    Host: {{host}}
    Content-Type: application/x-www-form-urlencoded
    Referer: {{page_url}}

    AUTH_FORM=Y&TYPE=AUTH&USER_LOGIN={{login}}&USER_PASSWORD={{password}}&{{form_fields}}
```

Пустая строка между заголовками и телом обязательна. Тело — одна строка.

| Подстановка | Значение |
| --- | --- |
| `{{action}}` | Путь и query-параметры action найденной формы |
| `{{host}}` | Хост и порт этой формы; протокол берётся из её URL |
| `{{page_url}}` | URL страницы входа для Referer |
| `{{origin}}` | Протокол, хост и порт страницы входа для Origin |
| `{{login}}` | Текущий логин; использовать целиком как значение одного поля |
| `{{password}}` | Текущий пароль; использовать целиком как значение одного поля |
| `{{form_fields}}` | В режиме формы — остальные актуальные поля; в режиме страницы Bitrix — только перечисленные `csrf_fields` |

Логин и пароль URL-кодируются автоматически: `&`, `+`, `=`, пробелы и кириллица
не превращаются в дополнительные параметры. Служебные константы в теле
записывайте URL-кодированными, например `label=%D0%92%D1%85%D0%BE%D0%B4`.
`{{form_fields}}` обязателен один раз; явно перечисленные поля не дублируются.
`AUTH_FORM=Y` и `TYPE=AUTH` проверяются: отсутствующие поля добавляются, а
конфликт с актуальной формой останавливает отправку. Пустые константы (`backurl=`)
допустимы. Пароль и логин тоже должны встречаться ровно по одному разу,
а их имена — совпадать с полями, которые подтвердил детектор модуля 3.

В режиме `action: form` вместо `{{action}}` можно указать конкретный путь,
например `/bitrix/admin/index.php`; он должен совпасть с фактическим action
формы. В режиме `action: fixed`, который использует `bitrix.yaml`, указывается
известный путь POST на том же origin, например `/bitrix/admin/?login=yes`.
Отправка на другой хост не поддерживается.

Дополнительные постоянные заголовки, например `X-Requested-With: XMLHttpRequest`,
поддерживаются. `Cookie`, `Authorization`, `Content-Length`, транспортные заголовки
и `User-Agent` из захваченного запроса копировать не нужно: cookies берутся из
свежей сессии, длина вычисляется, User-Agent задаётся настройкой запуска.
Фиксированные cookies/CSRF-токены в шаблон не помещайте. Для дополнительных имён
токенов служит `csrf_fields`; их значения приходят через `{{form_fields}}`.

Шаблон проверяется при `pointfinder --list-templates` и повторно при чтении отчёта
модулем 4. В отчёте к `raw` добавляются нормализованные служебные настройки;
редактировать нужно исходный YAML, после чего заново выполнить поиск.

- `transport: auto` — начать с HTTP. Если предварительная загрузка не смогла
  восстановить форму, допускается headless Chromium **до** отправки пароля.
  После отправленного POST повторной попытки через другой транспорт нет.
  CAPTCHA/OTP/429 не запускают такой повтор. `transport: http` отключает fallback.
- Поддерживается `POST` и `application/x-www-form-urlencoded`. Это описание
  HTTP-запроса, не произвольный TCP-пакет и не синтаксис Nuclei.
- `session: fresh` — новая cookie-сессия, GET формы и свежие скрытые поля
  перед каждой парой. В браузере используется отдельный контекст.
- `csrf_fields: [sessid]` — имена динамических токенов. В режиме страницы
  Bitrix перечисленный токен должен присутствовать в свежем ответе. В режиме
  обычной формы он может отсутствовать, но найденное значение должно
  обновиться. Пустой/исчезнувший токен не заменяется старым значением из отчёта.
- При браузерном fallback сначала прогружается форма и обновляются её поля;
  исходящий form-POST формируется по этому же `raw`. Если JavaScript вместо него
  отправляет JSON, меняет адрес или шифрует поля, запрос не подменяется наугад:
  выводится несоответствие HTTP-шаблону. При HTTP replay из браузерного захвата
  также используются актуальный шаблон, свежие cookies и токены.

Старое структурированное описание `method/action/encoding/session/defaults/csrf_fields`
без `raw` по-прежнему поддерживается. Для новых шаблонов удобнее показанный
выше вариант; дублировать константы и метод в YAML не требуется.

### Определение результата

Нужен хотя бы один признак результата: правило в `success_any`/`failure_any`
либо `success_status`/`failure_status`. Оба списка могут быть пустыми при
проверке только по коду. Остальные списки можно оставить `[]`.

| Список | Результат |
| --- | --- |
| `success_any` | Подтверждённый вход; только после отправки, HTTP 2xx и без видимого поля пароля |
| `failure_any` | Явное сообщение об отклонении учётных данных |
| `captcha_any` | Остановка без решения CAPTCHA |
| `mfa_any` | Требуется второй фактор; не считать полностью завершённым входом |
| `csrf_error_any` | Ошибка сессии/токена; не считать неверным паролем |

Поддерживаемые признаки (по одному ключу на правило):

- `text_contains: ...` — подстрока видимого текста без учёта регистра;
  скрипты, стили и явно скрытые HTML-узлы не учитываются.
- `in_body: '...'` — буквальная подстрока тела HTTP-ответа, включая HTML-теги,
  атрибуты и JSON, с учётом регистра. В браузерном режиме — HTML текущего DOM.
  Используйте уникальный для результата фрагмент, а не общий текст страницы.
- `input_name: USER_OTP` — доступное видимое поле с точным `name`;
  разрешено в CAPTCHA/MFA. В Bitrix это `captcha_word` и `USER_OTP`.
- `link_query: {logout: "yes"}` — видимая ссылка того же origin с указанными
  query-параметрами и точными значениями. Ссылка не открывается.
- `form_fields: {logout: "yes"}` — форма того же origin с этими значениями
  полей (включая скрытые) и доступной видимой кнопкой отправки. Поля из разных
  форм не объединяются. Кнопка выхода не нажимается.

В HTTP оцениваются HTML и inline-видимость; при нативной браузерной отправке
прежнего режима — фактическая видимость элементов. Шаблон страницы отправляет
HTTP-запрос и оценивает HTTP-ответ. Признак успеха до отправки не подтверждает пару.
Совпадение успеха и отказа даёт неопределённый результат. Если правила не
совпали, HTTP 200/303, cookie или оставшаяся форма сами по себе не означают
ни успешный, ни неуспешный вход. Универсальная обработка 429 и защитных страниц
продолжает действовать и имеет приоритет над признаками успеха.

### Границы поддержки

Основной `bitrix` рассчитан на административный вход 1С-Битрикс;
`bitrix-site` сохраняет прежнюю проверку стандартных HTML-форм сайта.
Он не объявляет поддержку всех версий облачного Bitrix24/SSO, изменённых
полей, JSON API или произвольных механизмов шифрования. Для них нужны
свои проверенные правила/сценарии. Правила не отменяют scope, лимиты и аудит.
